| Джерело | PID процесу sleep |
|---|---|
| `docker exec probe ps` |1 |
| `docker top probe` | 465|
| `docker inspect` |465 |

**Пояснення різниці номерів.**
docker exec probe ps показує PID у власному PID namespace контейнера (де основний процес контейнера sleep 3600 має PID 1). Натомість docker top probe і docker inspect -f '{{.State.Pid}}' probe звертаються до демона Docker на рівні хост-середовища (Linux VM/WSL 2) і показують глобальний PID цього самого процесу 465 у просторі імен хоста
>

**Звідки береться ім'я хоста контейнера.**
за замовчуванням Docker встановлює hostname рівним скороченому ідентифікатору контейнера (4546e1c27d07)

**Найбільший шар: яка інструкція, з чого складається.**
Серед власних інструкцій `Dockerfile` найбільший шар створила інструкція `RUN npm install` (`15.6MB`) — він складається з каталогу `node_modules` (встановлений пакет `express` і його транзитивні залежності) та службових файлів/кешу `npm`. Якщо розглядати образ повністю разом із шарами базового образу `FROM node:22`, то найбільшими є системні шари Debian Bookworm (`619MB` та `194MB` — встановлення системних пакетів і інструментів збірки через `apt-get`) і шар встановлення самого рантайму Node.js (`213MB`).

## Завдання 5. Ліміт пам'яті

Ліміт: 128 МБ

| N, МБ | Код завершення |
|---|---|
| ліміт / 2 = |0 |
| ліміт × 2 = |137|

```
вивід docker inspect для контейнера oom
OOMKilled=true Exit=137
```

Пошук максимального N:

| Спроба | N, МБ | Код завершення |
|---|---|---|
| 1 | 110 | 0 |
| 2 | 120 | 0 |
| 3 | 124 | 137 |
| 4 | 122 | 0 |
| 5 | 123 | 0 |

Максимальне N, що завершується з кодом 0: 123 МБ

**Що означає код завершення і як його отримано.**
Код завершення `137` обчислюється як `128 + 9`, де `9` — номер сигналу `SIGKILL`. Оскільки контейнер перевищив жорсткий ліміт пам'яті cgroup (`128` МБ) за вимкненого swap (`--memory-swap=128m`), ядро Linux (OOM killer) примусово завершило процес сигналом `SIGKILL`, що підтверджує вивід `OOMKilled=true Exit=137` у `docker inspect`.
> 

**Чому максимальне N менше за ліміт, на що витрачається різниця.**
Ліміт `128` МБ обмежує сумарне споживання оперативної пам'яті всім контейнером (cgroup), а не лише самим об'єктом `b`. Різниця між `128` МБ та знайденим максимальним `N` витрачається на запуск і роботу процесу інтерпретатора Python (завантаження бінарного файлу, стандартної бібліотеки, стек, внутрішні структури алокатора пам'яті `pymalloc`) та накладні витрати середовища контейнера.

## Завдання 6. PID 1 і сигнали

**Прогноз часу зупинки.**

| Конфігурація | Прогноз, с |
|---|---|
| А. exec-форма |0.1-0.5с |
| Б. через shell |10с |
| В. з `--init` |0.1-0.5с |

| Конфігурація | Дерево процесів (`docker top`) | Час зупинки, с | Код завершення |
|---|---|---|---|
| А | `881 (PPID 856) node index.js` | 3.40 | 137 |
| Б | `973 (PPID 950) sh -c node index.js` → `989 (PPID 973) node index.js` | 3.39 | 137 |
| В | `1074 (PPID 1049) /sbin/docker-init -- docker-entrypoint.sh node index.js` → `1087 (PPID 1074) node index.js` | 0.33 | 143 |

**Пояснення результату А.**

> У exec-формі `node index.js` запускається безпосередньо як основний процес контейнера з **PID 1** усередині його PID namespace. У Linux ядро захищає PID 1 від сигналів за замовчуванням: якщо процес не зареєстрував власний обробник `SIGTERM` (а в нашому застосунку його навмисно немає), `SIGTERM` від `docker stop` ігнорується. Дочекавшись таймауту зупинки (у цьому середовищі ~3 с), Docker надіслав неперехоплюваний `SIGKILL` (сигнал 9), тому контейнер завершився з кодом `137` (`128 + 9`).

**Пояснення результату Б.**

> При запуску через `sh -c "node index.js"` процес `sh` стає **PID 1** у контейнері, а `node index.js` — його дочірнім процесом (`PPID 973`). Команда `docker stop` надсилає `SIGTERM` лише процесу з PID 1 (`sh`), який не пересилає сигнал дочірньому процесу `node` і чекає на його завершення. Після вичерпання таймауту Docker примусово завершив процеси сигналом `SIGKILL`, повернувши код `137` (`128 + 9`).

**Пояснення результату В.**

> Прапорець `--init` запускає легкий init-процес `/sbin/docker-init` (`tini`) як **PID 1**, а `node index.js` працює як його дочірній процес (не PID 1). Отримавши `SIGTERM` від `docker stop`, `docker-init` прокинув сигнал дочірньому `node index.js`. Оскільки `node` тут не має статусу PID 1, для нього спрацювала стандартна дія ядра на `SIGTERM` (сигнал 15) — негайне завершення за `0.33` с із кодом `143` (`128 + 15`).
