# Лабораторна робота 1. Контейнеризація

Дисципліна: Конструювання програмного забезпечення

## Мета

Зібрати образ власного застосунку. Дослідити кеш збірки, багатоетапну збірку, обмеження ресурсів, поведінку процесу з PID 1 і публікацію образу в registry.

## Середовище

- Linux з Docker Engine або Windows з Docker Desktop (бекенд WSL 2).
- Git, обліковий запис GitHub.
- Командний рядок: bash на Linux, PowerShell на Windows. Команди нижче наведено для bash, відмінності для PowerShell указано окремо.

| bash | PowerShell |
|---|---|
| `curl http://localhost:8080/` | `curl.exe http://localhost:8080/` |
| `echo $?` | `echo $LASTEXITCODE` |
| `time docker stop app` | `Measure-Command { docker stop app }` |
| `TAG=$(git rev-parse --short HEAD)` | `$TAG = git rev-parse --short HEAD` |
| перенесення рядка `\` | перенесення рядка `` ` `` |

## Варіант

Варіант визначається логіном GitHub:

```bash
bash variant.sh <ваш-github-login>
```

На Windows скрипт запускається в Git Bash.

Вивід скрипта без змін вставляється у звіт. Значення з варіанта позначено нижче як `${НАЗВА}`, наприклад `${APP_PORT}`.

## Подання

1. Створити публічний репозиторій `kpz-lab1`.
2. Скопіювати в корінь бланк звіту `README.md` і заповнити його.
3. Структура репозиторію:

```
app/                 код застосунку і файл залежностей
Dockerfile           одноетапна збірка (завдання 2)
Dockerfile.bad       неправильний порядок інструкцій (завдання 3)
Dockerfile.multi     багатоетапна збірка (завдання 4)
.dockerignore
README.md            звіт
```

4. У звіт вставляється **фактичний вивід команд**, без скорочень і без редагування. Якщо вивід довгий, його можна обрізати, позначивши обрізане місце рядком `...`.

## Завдання 0. Перевірка середовища

```bash
docker version
```

Записати у звіт значення `OS/Arch` для Client і для Server.

## Завдання 1. Контейнер зсередини і ззовні

```bash
docker run -d --name probe alpine:3.20 sleep 3600
docker exec probe ps
docker top probe
docker inspect -f '{{.State.Pid}}' probe
docker exec probe hostname
docker ps --filter name=probe
docker rm -f probe
```

У звіті пояснити:

- чому номер процесу `sleep` у виводі `docker exec probe ps` відрізняється від номера в `docker top` і `docker inspect`;
- звідки береться ім'я хоста контейнера.

## Завдання 2. Застосунок і Dockerfile

### 2.1. Застосунок

Мова визначається `${STACK}`. Вимоги:

- HTTP-сервер слухає порт `${APP_PORT}`;
- запит `GET /` повертає JSON з двома полями:
  - `token`: значення змінної оточення `${ENV_NAME}`;
  - `hostname`: ім'я хоста, на якому працює процес;
- застосунок використовує залежність `${DEPENDENCY}`;
- застосунок не обробляє сигнали явно (це важливо для завдання 6).

Код розміщується в каталозі `app/`.

### 2.2. Dockerfile

Одноетапний `Dockerfile` на базовому образі `${SINGLE_BASE}`. Вимоги:

- файл залежностей копіюється і встановлюється до копіювання решти коду;
- команда запуску записана в exec-формі;
- є `.dockerignore`.

### 2.3. Збірка і запуск

```bash
docker build -t kpz-app:single .
docker run -d --name app -p 8080:${APP_PORT} -e ${ENV_NAME}=${TOKEN} kpz-app:single
curl http://localhost:8080/
docker image ls kpz-app
docker history kpz-app:single
docker rm -f app
```

У звіті пояснити, яка інструкція Dockerfile дала найбільший шар і з чого він складається.

## Завдання 3. Кеш збірки

Для кожного сценарію записати, які кроки взято з кешу (`CACHED`), а які виконано, і загальний час збірки. Збірку запускати з `--progress=plain`, щоб бачити кожен крок.

| № | Сценарій | Команда |
|---|---|---|
| 3.1 | Збірка без кешу | `docker build --no-cache --progress=plain -t kpz-app:single .` |
| 3.2 | Повторна збірка без змін | `docker build --progress=plain -t kpz-app:single .` |
| 3.3 | Змінено один рядок коду: додано до відповіді поле `${CHANGE_FIELD}` зі значенням `true` | те саме |
| 3.4 | `Dockerfile.bad`: копіювання всього коду **до** встановлення залежностей. Зібрати один раз, змінити значення поля `${CHANGE_FIELD}` на `false`, зібрати повторно | `docker build --progress=plain -f Dockerfile.bad -t kpz-app:bad .` |

Перед сценаріями 3.3 і 3.4 записати у звіт **прогноз**: які кроки буде виконано заново. Після збірки порівняти прогноз із результатом.

## Завдання 4. Багатоетапна збірка

`Dockerfile.multi`: перший етап збирає застосунок і встановлює залежності, фінальний етап базується на `${FINAL_BASE}` і містить лише те, що потрібно для запуску.

```bash
docker build -f Dockerfile.multi -t kpz-app:multi .
docker run -d --name app -p 8080:${APP_PORT} -e ${ENV_NAME}=${TOKEN} kpz-app:multi
curl http://localhost:8080/
docker rm -f app
docker image ls kpz-app
docker history kpz-app:multi
```

У звіті:

- порівняти розміри образів `single` і `multi`;
- перелічити конкретно, що є в образі `single` і відсутнє в `multi` (не менше трьох пунктів, кожен перевірений командою або виводом `docker history`).

## Завдання 5. Ліміт пам'яті

Завдання виконується на образі `python:3.12-slim` незалежно від варіанта. Команда виділяє `N` мегабайтів пам'яті:

```bash
docker run --rm --memory=${MEM_LIMIT_MB}m --memory-swap=${MEM_LIMIT_MB}m python:3.12-slim \
  python -c "b = b'x' * (N*1024*1024)"
echo $?
```

`--memory-swap`, рівний `--memory`, забороняє контейнеру використовувати swap.

5.1. Запустити з `N` = `${MEM_LIMIT_MB}` / 2 і `N` = `${MEM_LIMIT_MB}` × 2. Записати коди завершення.

5.2. Повторити запуск з `N` = `${MEM_LIMIT_MB}` × 2 без `--rm` і з `--name oom`, потім:

```bash
docker inspect -f 'OOMKilled={{.State.OOMKilled}} Exit={{.State.ExitCode}}' oom
docker rm oom
```

5.3. Експериментально знайти найбільше ціле `N`, за якого команда завершується з кодом 0. Записати всі спроби в таблицю.

У звіті пояснити:

- що означає код завершення і як його отримано;
- чому знайдене максимальне `N` менше за ліміт і на що витрачається різниця.

## Завдання 6. PID 1 і сигнали

Використовується образ `kpz-app:single`. Для кожної конфігурації запустити контейнер, переглянути дерево процесів і виміряти час зупинки:

```bash
docker run -d --name app kpz-app:single              # конфігурація А
docker top app -o pid,ppid,args
time docker stop app
docker inspect -f '{{.State.ExitCode}}' app
docker rm app
```

| Конфігурація | Запуск |
|---|---|
| А. exec-форма | `docker run -d --name app kpz-app:single` |
| Б. через shell | `docker run -d --name app kpz-app:single sh -c "<команда запуску вашого застосунку>"` |
| В. з init-процесом | `docker run -d --name app --init kpz-app:single` |

Перед вимірами записати у звіт **прогноз** часу зупинки для кожної конфігурації.

У звіті пояснити кожен результат: який процес отримав SIGTERM, що з ним сталося, чому код завершення саме такий.

## Завдання 7. Публікація в registry

7.1. Закомітити код і Dockerfile-и. Позначити образ коротким SHA коміту і опублікувати в GitHub Container Registry. Ім'я образу в GHCR має бути в нижньому регістрі.

```bash
TAG=$(git rev-parse --short HEAD)
docker login ghcr.io -u <login>        # пароль: personal access token з правом write:packages
docker tag kpz-app:multi ghcr.io/<login>/kpz-app:$TAG
docker push ghcr.io/<login>/kpz-app:$TAG
```

Записати дайджест з виводу `docker push`. Зробити пакет публічним у налаштуваннях GitHub.

7.2. Змінність тегу:

1. Опублікувати той самий образ з тегом `demo`.
2. Змінити код, перезібрати `kpz-app:multi`, знову опублікувати з тегом `demo`.
3. Записати обидва дайджести.
4. Видалити локальні образи `ghcr.io/<login>/kpz-app` і завантажити першу версію за дайджестом:

```bash
docker pull ghcr.io/<login>/kpz-app@sha256:<перший дайджест>
```

У звіті пояснити, що отримає користувач, який виконає `docker pull ghcr.io/<login>/kpz-app:demo`, і чому розгортання за тегом `demo` не є відтворюваним.

## Обов'язкові розділи звіту

**Питання, яке лишилось без відповіді.** Одне питання, яке виникло під час роботи і на яке не вдалося відповісти. Питання прив'язується до конкретного рядка звіту. Описати, що було зроблено, щоб на нього відповісти (джерело, експеримент), і де зупинились.

**Декларація використання ШІ.** Для кожного завдання вказати, чи використовувався ШІ, який інструмент і для чого. Спостереження, виміри і висновки мають бути власними. Відсутність декларації або її невідповідність звіту розглядається на захисті.
